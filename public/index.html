Idempotencia y concurrencia para entrevistas

Dos problemas clásicos de entrevista que parecen iguales y no lo son.

Este laboratorio nació para responder una pregunta concreta: cómo evitar duplicar un pago y cómo evitar vender más stock del disponible. El chat es sólo el vocabulario; el tema real es cómo coordinar reintentos y escrituras concurrentes sobre estado compartido.

Respuesta de entrevista, en 60 segundos

«¿Cómo manejarías la concurrencia en el stock y la idempotencia en el pago?»

0

Lo primero: separar los dos problemas

Suenan a lo mismo y no lo son. Descontar stock es un problema de concurrencia: muchos compitiendo por el mismo recurso. Cobrar es un problema de idempotencia: el mismo cliente reintentando la misma operación. Se resuelven con herramientas distintas y decirlo primero ordena toda la respuesta.

1

Stock — que la condición viaje en el WHERE

«Nunca leo el stock, decido en la aplicación y después escribo: entre esas dos cosas entra otro request. Lo hago en una sola sentencia.» 

UPDATE productos SET stock = stock - $2
 WHERE id = $1 AND stock >= $2;

«Si devuelve 0 filas, no había stock — y eso no es un error, es la respuesta de negocio. Lee, compara y descuenta en un solo acto atómico, sin un SELECT previo ni una ventana intermedia. PostgreSQL igual toma el lock de la fila mientras escribe: si ese producto está caliente, los updates compiten ahí. Debajo dejo un CHECK (stock >= 0) como red.»

2

Pago — una etiqueta del cliente y una constraint

«El cliente manda una idempotency key que genera él y repite en cada reintento. El servidor la reclama con un INSERT sobre una tabla con UNIQUE (actor, ruta, key). El INSERT es la verificación — no consulto antes, porque entre la consulta y el insert hay una ventana.»

«Si el insert gana, ejecuto el cobro y guardo la respuesta en la misma transacción. Si choca contra la constraint, ese error no es una falla: significa que otro llegó primero. Ahí miro qué pasó con esa key: si ya tiene respuesta la devuelvo tal cual, y si está en curso contesto 409 con Retry-After.»

«Guardo también un fingerprint del pedido. Si vuelve la misma key con otro contenido, es un bug del cliente: rechazo sin ejecutar, en vez de devolverle la respuesta de otra compra.»

3

Lo que cierra la respuesta

«En los dos casos la decisión tiene que ser atómica y vivir donde está el dato: para stock es un UPDATE ... WHERE stock >= cantidad; para idempotencia es un INSERT contra UNIQUE (actor, ruta, key), evitando leer, decidir en un if y escribir después.»

«Y no lo pongo en memoria ni en Redis porque tengo varias réplicas: cada una tendría su propia verdad. La coordinación va donde ya está el dato.»

Si repreguntan

¿Y si el pago falla después de descontar? No descuento: reservo con un TTL. Cobro, y confirmo o libero. Las reservas vencidas las barre un job idempotente. Es una saga con compensación.
¿Y si el proceso muere después de reclamar la key? La key queda tomada para siempre. Por eso la reserva tiene vencimiento: cuando expira, otro proceso puede retomarla.
¿Y si no estaba muerto, sino pausado? Ahí hace falta fencing: un contador que sube cada vez que alguien retoma. El proceso viejo cierra con el número anterior, actualiza 0 filas y su efecto se descarta.
¿Por qué no SELECT … FOR UPDATE para el stock? Funciona. El update condicional también toma un lock de fila, pero evita el viaje previo de lectura y mantiene condición y escritura en una sentencia. El FOR UPDATE hace falta cuando la decisión no cabe en el WHERE — por ejemplo, asignar el próximo número de orden.
¿Y si el cobro lo hace un proveedor externo? Ahí la transacción ya no cubre el efecto. O el proveedor acepta su propia idempotency key, o uso outbox: guardo la intención en la transacción y un worker la ejecuta. Exactly-once no existe a través de una red.
¿Qué nivel de aislamiento usás? READ COMMITTED, el default, con constraints y updates condicionales. Subir el nivel no elimina el problema: lo convierte en errores de serialización que igual hay que reintentar.

Todo lo que sigue en esta página es el respaldo de estas seis respuestas: por qué cada pieza está, qué se rompe si falta, y los escenarios corriendo contra tres réplicas reales para verlo pasar.

Varios procesos modifican el mismo estado

Concurrencia

La pregunta es «¿qué pasa si llegan juntos?». La protección se elige por invariante: constraint, lock de fila, update condicional o transacción.

Elegir la herramienta correcta →

Regla común: la base decide en el mismo acto que escribe. La aplicación interpreta si ganó, perdió o no había nada que cambiar.

Idempotencia

Una operación es idempotente si ejecutarla muchas veces deja el sistema igual que ejecutarla una sola vez.

Qué problema resuelve

Tu request falla con timeout: no con un error claro, sino con silencio. Ahora estás en una de tres situaciones y no podés distinguirlas:

  1. 1 no llegó al servidor
  2. 2 llegó, se ejecutó, y se perdió la respuesta
  3. 3 llegó y no se ejecutó

En 1 y 3 hay que reintentar. En 2, reintentar duplica — cobrás dos veces, mandás el mensaje dos veces. La idempotencia existe para que no tengas que distinguirlas: reintentás siempre y el servidor decide.

Cuándo recurrir a ella

¿La operación crea o modifica algo? si no → no hace falta
¿Ejecutarla dos veces hace daño real? si no → no hace falta
¿El cliente puede reintentar, aunque sea a mano? las tres sí → necesitás key

Casos típicos: cobrar un pago, crear un pedido, mandar un mensaje o un email, crear una reserva de stock o transferir dinero.

Cuándo NO: GET no cambia nada; DELETE /users/123 borrado dos veces sigue siendo borrado; PUT con el estado completo deja el mismo resultado final.

Y el atajo que casi nadie menciona: si el cliente elige el ID del recurso —PUT /orders/9f2c-4a1b— entonces ese ID ya es la key. Un UNIQUE sobre él hace todo el trabajo y no hace falta agregar nada encima. Antes de meter idempotency keys, preguntate si podés rediseñar el endpoint así.

Cómo se resuelve, mínimo viable

la tabla

CREATE TABLE idempotency_keys (
  actor_id    uuid NOT NULL,
  route       text NOT NULL,
  key         text NOT NULL,
  fingerprint text NOT NULL,  -- hash del pedido
  response    jsonb,           -- NULL = en curso

  PRIMARY KEY (actor_id, route, key)
);

el flujo

1. INSERT de la key   ← sin SELECT previo

2. ¿ganó el INSERT?
     sí → ejecutá el efecto y guardá la
          respuesta en la misma transacción

     no → alguien llegó primero:
          fingerprint distinto → 409
          hay respuesta       → devolvela
          no hay todavía      → 409 en curso

Dos decisiones cargan todo el peso. Primera: el INSERT es la verificación, sin un SELECT que pregunte «¿existe?», porque entre esa consulta y el INSERT hay una ventana por la que entran los otros requests.

Segunda: la respuesta se guarda en la misma transacción que el efecto. Si están separadas y el proceso muere en el medio, el pago existe pero el reintento no encuentra nada que devolver.

El fingerprint es un hash canónico del pedido y responde otra pregunta: si el cliente reusó la etiqueta para otro contenido. Sin él, un cliente con un bug recibe la respuesta del pedido anterior creyendo que el suyo se hizo. La key dice «es el mismo intento» y la decide el cliente; el fingerprint dice «el cliente está usando bien esa etiqueta» y lo verifica el servidor.

El protocolo completo — no alcanza con la key

La key sola es un rótulo. Lo que hace que funcione es una secuencia de decisiones, y cada una tapa un agujero distinto. La forma de demostrar que entendiste el tema no es enumerar los pasos: es saber qué se rompe si sacás cada uno.

# El paso Qué se rompe si falta
1 El cliente genera la key y la persiste antes de mandar Si la genera el servidor, el reintento trae una key nueva y es un pedido nuevo. Si el cliente no la guarda y se reinicia, tampoco puede reintentar.
2 Scope (actor, ruta, key), no key sola Dos clientes que eligen el mismo UUID —o alguien que manda "1"— se pisan entre sí.
3 Reclamarla con un INSERT, nunca con SELECT y después INSERT La ventana. Es el bug del 90% de las implementaciones: N requests leen «no existe» y N ejecutan.
4 Fingerprint canónico del pedido, guardado junto a la key Un cliente que reusa la etiqueta para otro contenido recibe la respuesta del pedido anterior y cree que el suyo se hizo. Silencioso.
5 Estado de la operación: en curso / completada / fallida Sin estado no podés distinguir «ya terminó, tomá el resultado» de «hay alguien ejecutándolo ahora mismo».
6 Guardar la respuesta en la misma transacción que el efecto Si el proceso muere entre ambas, el cobro existe y el reintento no encuentra nada que devolver: o duplica, o queda colgado para siempre.
7 Lease sobre la operación en curso una reserva con fecha de vencimiento: «esta operación es mía hasta las 10:04:30» El proceso dueño se muere y la key queda reclamada para siempre. Esa operación no se puede reintentar nunca más. El lease existe porque no se puede saber si un proceso murió o está lento: en vez de preguntar «¿sigue vivo?», se pregunta «¿su reserva venció?».
8 Fencing: un contador que sube cada vez que alguien retoma El dueño viejo revive —estaba en una pausa de GC, no muerto— y completa una operación que ya tomó otro. Dos efectos. El fencing es la consecuencia inevitable del lease: si el vencimiento es una apuesta sobre el tiempo, hay que cubrirse por si se pierde.
9 TTL y barrido de las keys viejas La tabla crece para siempre; no es una falla de corrección, sino de operación, y aparece a los seis meses.
10 Una unicidad propia del dominio, además de la de la key Si el cliente regenera la key en el retry, la primera red no lo detecta. Hace falta una segunda: UNIQUE (cuenta, referencia_externa).
11 El cliente reintenta con backoff exponencial y jitter Mil clientes que fallaron juntos reintentan juntos y vuelven a tirar el servicio. Sin jitter, la recuperación se convierte en el segundo incidente.

Los pasos 1 a 6 son el mínimo para que la idempotencia sea correcta. Del 7 al 9 son para que sobreviva a procesos que se mueren y al paso del tiempo. El 10 y el 11 son los que casi nadie menciona en una entrevista, y son los que muestran que lo implementaste de verdad.

Si te preguntan «¿y si el proceso muere justo después de reclamar la key?» — esa es la pregunta del paso 7, y la respuesta es el lease. Si siguen con «¿y si no estaba muerto sino pausado?», es la del 8, y la respuesta es el fencing.

El error que se comete siempre

// ❌ parece una protección, no lo es
const existe = await db.query('SELECT ... WHERE key = $1');
if (existe) return replay(existe);
await db.query('INSERT ...');   // ← entre las dos líneas entraron 59 requests

En READ COMMITTED —el nivel por defecto de PostgreSQL— ninguna transacción ve las filas no confirmadas de otra. Los 60 leen «no existe» y los 60 crean el registro. Correlo y mirá el número: cambia en cada corrida.

El límite: cuando el efecto sale de la base

Todo lo anterior descansa en una sola cosa: que el efecto y el registro de la respuesta entren en la misma transacción. Si el efecto es cobrar con un proveedor externo, mandar un email o publicar en una cola, eso ya no se cumple. 

BEGIN;
  INSERT INTO pagos ...;
  await stripe.charge(...);   ← esto NO está en la transacción
COMMIT;                    ← y si falla acá, ya cobraste

Las dos salidas, y conviene nombrarlas:

  1. A El proveedor también es idempotente. Stripe, por ejemplo, acepta su propia Idempotency-Key. Le pasás la tuya —o una derivada— y el problema se resuelve del otro lado.
  2. B Outbox. En la transacción escribís sólo la intención («hay que cobrar esto»). Un worker aparte la lee y la ejecuta con reintentos. La base y la intención commitean juntas; la llamada externa se hace después, y puede repetirse sin daño porque el proveedor es idempotente o porque la marcás como hecha al volver.

Exactly-once no existe a través de una red.

Lo que existe es at-least-once más idempotencia en el receptor. Si alguien te dice que su sistema es exactly-once, o tiene un receptor idempotente y no lo llama así, o está equivocado.

Concurrencia sobre estado compartido

Varios procesos, sin memoria compartida, tocando el mismo dato al mismo tiempo. Ninguno sabe qué están haciendo los otros.

Por qué no alcanza con escribir con cuidado

Todo bug de concurrencia tiene la misma forma: una ventana entre leer y escribir. 

t0  proceso A  lee   saldo = 100
t1  proceso B  lee   saldo = 100    ← nadie hizo nada mal
t2  proceso A  escribe saldo = 90
t3  proceso B  escribe saldo = 90   ← se perdió un descuento

Con un solo proceso no pasa nunca. Con tres réplicas pasa a veces — y «a veces» es lo peor que le puede pasar a un bug: pasa el code review, no aparece en desarrollo, y llega a producción.

Un mutex en memoria no sirve: cada réplica tiene el suyo. Redis tampoco resuelve el fondo, agrega una segunda autoridad que puede desincronizarse con la base. La coordinación correcta va donde ya está el dato.

Las cuatro herramientas, y cuándo usar cada una

1

Constraint única

cuando la regla es «no puede haber dos» 
UNIQUE (actor_id, route, key)
-- el INSERT falla con 23505 y ESE error es la respuesta útil

La más barata y la más fuerte: no hay ventana posible porque la decisión y la escritura son el mismo acto. Si tu regla se puede expresar como unicidad, empezá acá. Sirve incluso si la aplicación tiene un bug.

2

Lock pesimista

cuando hay que leer, calcular y escribir 
SELECT next_sequence FROM counters
 WHERE id = $1 FOR UPDATE;   -- nadie más pasa hasta el COMMIT

Para «dame el siguiente número» no hay atajo: alguien tiene que esperar. Serializa, así que el lock debe ser lo más chico posible (una fila, no una tabla) y la transacción lo más corta posible. Regla de oro: si tomás más de un lock, tomalos siempre en el mismo orden en todo el código, o vas a tener deadlocks.

3

Update condicional

cuando la condición se puede escribir en SQL 
UPDATE receipts SET state = 'read', version = version + 1
 WHERE id = $1 AND version = $2          -- compare-and-set
   AND rank(state) < rank('read');      -- sólo avanza

-- ¿0 filas actualizadas? no es un error: es la respuesta correcta

No necesita un SELECT ... FOR UPDATE previo. Como toda escritura, toma brevemente el lock de la fila; la ventaja es que la condición viaja en el WHERE y se evalúa en el mismo acto que el cambio. Es ideal para máquinas de estado monotónicas y para fencing.

4

Transacción

cuando varios efectos son indivisibles 
BEGIN;  -- todo lo de adentro es invisible para los demás
  … mensaje, contador, snapshot de entrega, respuesta …
COMMIT;  -- aparece todo junto, o no aparece nada

No es una herramienta de exclusión: es de atomicidad. Su superpoder es que elimina los estados intermedios observables — y con eso elimina la pregunta «¿me quedé a la mitad?», que es la que obliga a escribir lógica de recuperación.

El caso que más se pregunta: descontar stock

Es el ejercicio clásico porque tiene las dos mitades: cobrar necesita idempotencia, descontar stock necesita control de concurrencia. Y la solución del stock cabe en una sentencia.

el bug clásico

SELECT stock FROM productos WHERE id = $1;
-- lee 1

if (stock >= 1) {         ← LA VENTANA
  UPDATE productos
     SET stock = stock - 1
   WHERE id = $1;
}
-- dos requests pasan el if. stock = -1
-- vendiste algo que no tenías: overselling

una sola sentencia

UPDATE productos
   SET stock = stock - 1
 WHERE id = $1
   AND stock >= 1;   ← la condición va acá

-- ¿0 filas? no había stock.
-- Sin SELECT previo ni ventana read/if/write.

CHECK (stock >= 0)  -- la red debajo

El UPDATE condicional lee, decide y escribe en un solo acto atómico, sin un instante entre la comparación y la resta. «0 filas afectadas» es la respuesta de negocio: no hay stock.

Las repreguntas que siguen, y la respuesta corta de cada una:

Te preguntan Respondés
¿Y si el cliente compra 5 unidades? SET stock = stock - 5 WHERE stock >= 5. Mismo mecanismo.
¿Por qué no SELECT … FOR UPDATE? Funciona. Ambos caminos compiten por el lock de esa fila; el update condicional evita el SELECT previo y mantiene la decisión en una sentencia. Usá FOR UPDATE cuando necesites leer y decidir algo que no cabe en un WHERE.
¿Y si el pago falla después de descontar? Ahí no alcanza una sentencia: es una saga. Se reserva el stock con un TTL, se cobra, y se confirma o se libera. La reserva vencida la barre un job — y ese job tiene que ser idempotente.
¿Y si hay varios productos en el carrito? Ordená siempre por el mismo criterio (por ejemplo, product_id ascendente) antes de tocarlos. Dos carritos con los mismos productos en orden distinto se bloquean mutuamente: deadlock.
¿Y si el stock vive en Redis por performance? Ahí tenés dos autoridades que pueden desincronizarse. Redis sirve como caché de lectura o como rate limiter; la decisión de «hay o no hay» tiene que quedar donde está la transacción.

Niveles de aislamiento — el vocabulario

Nivel Evita Cuesta
READ COMMITTED
default en PostgreSQL		 lecturas sucias permite alta concurrencia, pero el lost update sigue siendo posible; las invariantes necesitan las herramientas de arriba
REPEATABLE READ + lecturas no repetibles. En PostgreSQL también aborta el lost update errores de serialización que tenés que reintentar vos
SERIALIZABLE + phantom reads y write skew más abortos y más contención bajo carga

La trampa: subir el aislamiento no elimina el problema, lo convierte en errores que tenés que reintentar. Y no te salva de nada si el chequeo está en un if de la aplicación en vez de en el WHERE.

La respuesta buena a «¿qué nivel usarías?» no es un nivel: es «depende del camino, y lo mediría». READ COMMITTED con constraints y updates condicionales cubre la mayoría de los casos de este laboratorio sin subir el aislamiento global. SERIALIZABLE con reintento se justifica cuando la invariante involucra varias filas y no se puede expresar en una operación atómica — el caso del write skew.

La regla que resume las cuatro

Poné la decisión en la escritura atómica, no en un if previo.

Puede ser una constraint que decide un INSERT, una condición en el WHERE o un FOR UPDATE que ordena una decisión compleja. Lo que no sirve es leer, decidir en la aplicación y escribir después con datos que ya podrían estar viejos.

Corolario práctico: «0 filas afectadas» es información, no un fallo. Significa «alguien llegó antes» o «esto ya estaba hecho», y casi siempre la respuesta correcta es leer lo que hizo el otro, no reintentar a ciegas.

Cómo cerrar la explicación

«Un cliente puede perder la respuesta y reintentar contra otra réplica. Varios dispositivos pueden confirmar al mismo tiempo. Aun así se crea un solo mensaje lógico, el estado sólo avanza y el orden se conserva.»

Y después, el mecanismo: la corrección no vive en la memoria de un proceso, porque hay tres. Vive en constraints, locks y updates condicionales de PostgreSQL. Cada afirmación se verifica consultando la base al final — contar respuestas 2xx no demuestra ninguna de estas propiedades.

Si te preguntan por la evidencia: en Kubernetes hay tres pods detrás de Traefik y una sola URL; una corrida real repartió requests entre los tres y dejó un solo mensaje en PostgreSQL. En Compose, la página reparte entre tres puertos porque ahí no hay balanceador.

Si te preguntan por los límites: PostgreSQL sigue siendo una sola instancia. Esto prueba consistencia de aplicación y routing multi-réplica, no alta disponibilidad de la base ni tolerancia de zona.

La carga sostenida, el pod-kill y la base degradada sí están medidos — con Toxiproxy entre la API y PostgreSQL, y auditando la base al final de cada corrida. El resultado que resume todo: con la base cortándose, 8599 operaciones, 1151 fallaron, 53 quedaron ambiguas, y las completadas coinciden exactamente con los mensajes escritos. Cero violaciones. Está en evidence/RESULTS.md, con el comando al lado de cada número.

Lo que sigue sin medirse está dicho igual de explícito: el costo en latencia de matar un pod (el ruido de la máquina se lo come) y el total de un request, que no está acotado porque los timeouts individuales se suman.

La diferencia entre alguien que estudió el tema y alguien que lo midió está en las cajas verdes. Cualquiera puede decir «uso una constraint»; muy pocos pueden decir «lo probé con 100 clientes concurrentes y quedó un mensaje».

Idempotencia

¿Cómo garantizás que un retry no duplique?

La key vive en una tabla con UNIQUE (actor, route, key). No hay un SELECT previo preguntando «¿existe?»: entre ese SELECT y el INSERT hay una ventana donde entra otro pod. La decisión es el INSERT — quien lo gana es el dueño y ejecuta; quien recibe el 23505 va a leer el resultado del dueño.

Medido: 12 requests con la misma key por el ingress, repartidos 4/4/4 entre tres pods → 1 creado, 11 replays, 1 mensaje en la base.
¿Y si dos requests con la misma key llegan al mismo instante a pods distintos?

Es el mismo caso: PostgreSQL serializa y uno gana la constraint. Eso es precisamente lo que hace que la solución no dependa de coordinación entre réplicas — no hace falta un lock distribuido ni un líder, porque la base ya es el punto de acuerdo.

¿Qué devolvés si la key es la misma pero el body cambió?

409, y no ejecuta nada. Se guarda un fingerprint canónico del efecto; si no coincide, es un error del cliente reusando una key. Se chequea antes que el estado de la operación: una key reusada es un error sin importar en qué estado esté la original. Eso es I2.

En los logs: el evento idempotencia.conflicto guarda los dos fingerprints — nunca el cuerpo, que es contenido del usuario.
¿Qué pasa si el dueño muere a mitad de la operación?

Toma un lease con vencimiento. Otro proceso puede retomarla cuando vence, y al hacerlo sube el attempt. Ese attempt es el fencing: si el dueño viejo revive e intenta cerrar, su UPDATE lleva WHERE attempt = <el suyo> y toca cero filas. El throw dispara el ROLLBACK y todo lo que creó se descarta.

Dos procesos pueden creerse vivos; lo que no pueden es creerse dueños del mismo intento.

¿Y quién decide si el lease venció?

PostgreSQL, siempre. Ningún reloj de la aplicación decide nada: con tres pods hay tres relojes y darían tres respuestas para la misma operación. El booleano viene calculado en el SELECT, no comparado en Node.

Ya nos mordió: un bug comparaba lease_until (escrito por Postgres) contra new Date(). Se manifestó como test intermitente. Hay un test de regresión con ese nombre exacto.
Una operación ambigua —el cliente nunca vio la respuesta—: ¿qué devolvés al reintentar?

Hay tres respuestas correctas, no dos: 200 si ya había terminado (replay), 201 si nunca llegó a ejecutarse, y 409 si el intento original todavía está corriendo. El 409 no es un fallo: es el mecanismo que impide el segundo efecto.

Lo que sí hay que exigirle al 409 es que converja. Un 409 eterno sería un cliente sin forma de averiguar si su envío existe, y eso sí sería un defecto.

Medido: 2174 operaciones ambiguas provocadas con un cliente que se rinde a los 12 ms. 1118 dieron 409 y los 1118 convergieron, en 2.14 intentos promedio. Base final: 4372 operaciones = 4372 mensajes.

Orden y concurrencia

¿Cómo asignás orden dentro de una conversación con tres réplicas?

Una fila por conversación en conversation_sequences, tomada con SELECT … FOR UPDATE dentro de la misma transacción que inserta el mensaje. Es un punto de serialización explícito y elegido.

Si el contador se incrementara fuera de esa transacción, un rollback dejaría un número de orden entregado a nadie: un agujero en la secuencia.

Se audita: el verificador chequea que max(server_sequence) sea igual a la cantidad de mensajes. Un agujero lo delata.
¿Lock pesimista u optimista?

Pesimista hoy, y la columna version existe para poder comparar con compare-and-set. No lo elegí a ojo: lo medí, y ahora tengo contra qué comparar el optimista.

Medido: en la conversación caliente el p95 es 59 ms contra 33 ms del resto (1.8×). Y con la base lenta, ese lock amplifica 100 ms en 6.6 segundos.
¿Qué hacés con un hueco en la secuencia de un dispositivo?

Buffereo el mensaje y abro un deadline. Si vence, el stream pasa a resync_required y el cliente tiene que declarar desde dónde sigue.

Nunca salto el hueco en silencio: eso sería publicar un stream con un agujero. Preservo orden y sacrifico disponibilidad de ese dispositivo, a propósito — esperar para siempre tampoco es una solución.

¿Por qué una «conversación caliente» y no simplemente más tráfico?

Porque el orden se asigna por (conversación, dispositivo): dos generadores sobre el mismo stream se pisan el client_sequence y producen conflictos que no tienen nada que ver con la carga.

El calor real es estructural: una conversación con 40 dispositivos en vez de 4. Cada uno tiene su stream, y aun así los 40 compiten por la única fila del contador. Ahí está el FOR UPDATE.

Kubernetes

¿Cómo probás que el tráfico se reparte de verdad?

Cada pod devuelve su nombre en X-Instance-Id. Y sobre todo: no uso kubectl port-forward para medirlo. No balancea — fija un pod y se queda ahí aunque apuntes al Service.

Costó tiempo descubrirlo: doce curl por port-forward dieron los doce al mismo pod. Por eso hay dos smoke tests, uno dentro del cluster y otro desde afuera por el ingress.
¿Por qué la probe de liveness no consulta la base?

Porque una base lenta es una dependencia compartida: reiniciar las tres réplicas no la arregla, y convierte una degradación en una caída total. Liveness pregunta «¿este proceso está vivo?», readiness pregunta «¿puede atender?». Son preguntas distintas.

Medido en L3: con la base cortándose durante 2 minutos, lab_ready se mantuvo en 3 y hubo 0 restarts.
¿El PodDisruptionBudget te protege de que se muera un pod?

No, y es el malentendido más común. Sólo intercepta la API de evicción: kubectl drain, el autoscaler, upgrades del cluster. Un kubectl delete pod pasa de largo, y un nodo que se apaga también.

Cubre interrupciones voluntarias. Para lo otro está el pod kill.

Probado con la API de evicción: primera 201, segunda inmediata 429 Cannot evict pod as it would violate the pod's disruption budget.
Pusiste una regla de reparto por nodo. ¿Alcanza con eso?

No, y me mordió. El topologySpreadConstraint se evalúa al planificar, y durante un rollout los pods viejos todavía cuentan para el skew. Cada colocación individual es legal y el resultado final igual viola la regla.

Se arregla con maxSurge: 0: el pod viejo se va antes de que se planifique el nuevo. Y Kubernetes no reequilibra nunca — si agregás un nodo, los pods se quedan donde están.

Pasó de verdad: el primer rollout con la regla puesta dejó 0 pods en un nodo y 2 en otro, sin ningún error.

Carga, medición y observabilidad

¿Modelo abierto o cerrado para la carga?

Abierto, y no es un detalle. Con VUs en bucle cerrado, cuando el sistema se frena el generador manda menos carga —cada VU espera su respuesta—, la cola nunca se forma y la degradación es imposible de ver: el test se autorregula y siempre da bien.

En modelo abierto las llegadas son independientes de las respuestas, así que si el sistema se frena la cola crece y se ve.

¿Cuál es tu cuello de botella?

El pool de conexiones, en 10. No es CPU ni el event loop: es cola por conexión.

Medido: a 100 ops/s hay 14 a 20 requests en vuelo por pod contra 10 conexiones, con 9 esperando, y el event loop nunca pasa de 65 ms. En la escalera de L4, pool waiting va 0 → 8 → 269 y es lo único que se mueve antes que la latencia. El codo está entre 100 y 200 req/s.

Lo que todavía no sé: si subir el pool mueve el codo o sólo traslada la contención al lock del contador. Eso es lo siguiente que mediría.

¿Cómo sabés que no perdiste ni duplicaste mensajes?

No cuento respuestas 2xx. Cada escenario termina consultando la base: npm run verify audita I1–I10 contra los datos y sale con código distinto de cero si algo se rompió.

El número que muestro: con la base cortándose, 8599 operaciones, 1151 fallidas, 53 ambiguas — y operaciones_completadas = mensajes, exacto. Cero violaciones.
¿Cómo sabés que tu verificador funciona?

Le inyecto violaciones reales y exijo que las encuentre. Un verificador que no puede fallar no verifica nada.

Y hay algo lindo: la violación de I2 no la pude inyectar — la constraint la rechaza antes con un 23505. Eso no es una limitación del test: es exactamente la evidencia que I2 pedía.

¿Métricas o logs? ¿Por qué los dos?

Contestan preguntas distintas y ninguna reemplaza a la otra:

Métrica → «¿cuántas operaciones terminaron en conflict?» (agregado, barato). Log → «¿qué le pasó exactamente a este envío?» (individual, caro).

Y no es que falte ganas de meter el messageId en una métrica: no se puede. Un id como label de Prometheus es cardinalidad infinita — una serie nueva por mensaje tumba al Prometheus antes que al servicio. La misma regla vale para los labels de Loki. Por eso los identificadores van dentro de la línea JSON y se filtran al leer.
